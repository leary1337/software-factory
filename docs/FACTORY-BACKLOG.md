## Задачи по поведению

Приоритет **P1** — закрыть до доверенного автоматического слияния;
**P2** — следующая очередь для надёжной повседневной работы;
**P3** — расширение за пределы текущего локального режима.
Идентификаторы ниже локальны для этого списка, это не созданные Seeds/GitHub issues.

### F01 P1 — исправлено: строгий вердикт и статус проверок

Результат PASS принимается только с точной первой строкой и двумя обязательными
полями: `REVIEWED_COMMIT: <40-символьный SHA>` и `QUALITY_GATE: PASS`.
Цитаты, конфликтующие заголовки, старый PASS без полей, FAIL/NOT_RUN и блок
`Not run:` не разрешают слияние. Промпт reviewer требует CHANGES при пропущенной
обязательной проверке. SHA результата сравнивается с сохранённой точкой ревью.

Код: `src/plan-runs/review-result.ts`, `review.ts`,
`src/registry/builtins/factory-roles.ts`. Регрессии: `review-safety.test.ts`,
`review.test.ts`. Это структурированное подтверждение reviewer; независимое
исполнение qualityGate сервером не добавлено. Реальный прогон роли — F06.

### F02 P1 — исправлено: слияние проверенного коммита и общая политика

SHA читается до запуска reviewer, сохраняется в событии и используется как
`baseCommit` его workspace. Если вершина PR изменилась, начинается новое ревью.
GitHub merge получает обязательный `sha`, поэтому push между проверкой и записью
merge отклоняется сервером GitHub. Ответ без `merged: true` не считается успехом.

Merge-on-PASS использует существующую политику `decideAutoMerge`: конфиг берётся
из удалённой базовой ветки, diff — из отдельного git snapshot; защищённые пути,
изменение `.warren/config.yaml` и непрочитанный diff запрещают merge. Старый reap
не включает auto-merge для implementer до независимого ревью.

Код: `src/plan-runs/review-forge.ts`, `src/runs/reap/auto-merge-arm.ts`,
`auto-merge-snapshot.ts`, `src/forge/github/provider.ts`.
Тесты: `review-forge.test.ts`, `src/forge/github/review-safety.test.ts`,
`auto-merge-arm.test.ts` и существующие snapshot/policy-тесты.

**Настройка:** для автоматического слияния нужны и
`WARREN_PLAN_RUN_MERGE_ON_PASS=1`, и `pr.autoMerge` в базовой ветке проекта.
Один глобальный флаг больше не обходит политику проекта. Самостоятельный
implementer вне plan-run требует ручного слияния: независимого review-step
в таком запуске нет.

### F03 P1 — исправлено: отмена активного review/rework

Отмена проверяет связанные review/rework-запуски и исходный implementer,
передаёт cancel активному runtime и не называет завершённый run отменённым.
Общий lock сериализует отмену и переходы координатора: после завершённой отмены
следующий шаг не стартует. Повторный cancel уже отменённого плана повторяет
незавершённую остановку, если первый запрос к runtime завершился ошибкой.

Код: `src/plan-runs/cancel.ts`, `lock.ts`, `coordinator.ts`.
Тесты: `cancel.test.ts`, `review-safety.test.ts` — review, rework, гонка spawn/cancel,
повтор после transport failure и освобождение счётчика после reap.
Остановка процесса и освобождение реального auth lease остаются частью F06.
При недоступном runtime ошибка логируется; требуется повторить cancel после
восстановления связи, автоматического фонового повтора cancel пока нет.

### F04 P1 — исправлено: восстановление шагов и доставки результата

Вердикт, попытки merge, подтверждение merge, попытки публикации и завершение
записываются отдельно. `review_finished` появляется после доставки либо
исчерпания лимита. Merge и комментарий имеют по три попытки; исчерпание отмечается
как `broken` и `needs_attention`, причина остаётся в событии.
После сбоя между merge и комментарием координатор завершает доставку, прежде чем
перейти к следующему тикету. Слитый SHA распознаётся без повторной записи merge.

Комментарий имеет стабильный маркер; перед повтором GitHub проверяется на уже
опубликованный отчёт, включая страницы истории. Слепые HTTP-повторы POST выключены.
Связь с review/rework сохраняется в callback после создания строки run, но до
вызова runtime. Ошибка callback завершает строку как `never_started` и не создаёт
sandbox. Перезапуск продолжает работу по событиям и не порождает второй reviewer.

Код: `src/plan-runs/review-delivery.ts`, `review.ts`, `in-flight.ts`,
`src/forge/github/review-comment.ts`, `src/runs/spawn/dispatch.ts`.
Тесты: `review-safety.test.ts`, `src/forge/github/review-safety.test.ts`,
`src/runs/spawn/admission.test.ts`.

Старые записи `review_finished`, созданные прежней версией, автоматически
не переигрываются: их PR нужно проверить вручную. Аварийная остановка живого
процесса и восстановление workspace проверяются отдельно в F06.

### F05 P1 — исправлено: общее ограничение запуска

Все пути через `spawnRun` резервируют слот до clone/runtime работы и учитывают
все незавершённые runs, включая ручные. Резерв заменяется строкой БД под общей
синхронизацией; тест со специально задержанным чтением проверяет эту гонку.
Ручной запрос получает понятный отказ до создания sandbox; план остаётся ждать,
а cron не расходует попытки и не теряет текущую задачу из-за занятого слота.

Лимит по умолчанию — один. Существующее имя env
`WARREN_AUTOMATIC_MAX_CONCURRENT_RUNS` сохранено, но теперь охватывает все
запуски. Окно `WARREN_AUTOMATIC_RUN_WINDOW` по-прежнему относится только к
автоматическому расписанию. Синхронизация рассчитана на один сервер-владелец БД.

Код: `src/runs/spawn/admission.ts`, `src/triggers/automatic-capacity.ts`,
`dispatch.ts`, `src/plan-runs/tick.ts`. Тесты: `admission.test.ts`,
`admission-race.test.ts`, `clone-lock.test.ts`, `automatic-capacity.test.ts`,
`dispatch.bounded-retry.test.ts`.

### F06 P1 Сквозная проверка новой цепочки и безопасной остановки

**Локальная часть исправлена и проверена на macOS, 2026-11-10.** Полный внешний
пилот с GitHub остаётся отдельным пунктом F06.1 ниже.

Исправлены подтверждённые дефекты:

- `cancel()` и повторная отмена дожидаются завершения drive-loop и сохранения
  credentials. Штатная остановка закрывает все локальные jobs; серверный
  entrypoint обрабатывает SIGINT/SIGTERM через `stop()`.
- На macOS отдельный контролирующий процесс останавливает группу процессов
  песочницы при потере IPC-соединения с сервером, в том числе после SIGKILL.
- До удаления прерванного или грязного workspace сохраняется автономный Git
  bundle: коммиты, изменения отслеживаемых файлов и новые неигнорируемые файлы.
  Это действует и при boot-reconcile, и при GC. Ошибка сохранения оставляет
  workspace на месте; путь bundle доступен в событии удаления и, для reap и
  boot-reconcile, в `salvagePath` запуска.
- Журнал вне HOME позволяет сохранить обновлённые Codex credentials после
  рестарта. Ошибка записи исходного auth-файла сохраняет временный файл и
  журнал для повторного восстановления. Manifest записывается атомарно;
  runtime не запускается, если сохранить manifest не удалось.
- Отдельный `runtime_event_seq` в SQLite/Postgres отделяет курсор runtime от
  служебных событий плана. Раньше короткий запуск мог потерять свой итоговый
  ответ и остаться `queued`; сквозной тест воспроизвёл это зависание.
- Потерянные reviewer/rework не получают отдельный автоматический retry вне
  координатора плана. Ревью после потери runtime требует внимания владельца.

Проверки: `src/plan-runs/runtime-chain.test.ts` проводит dispatch, подготовку
workspace, настоящий sandbox-exec, Git commit/push, event bridge, reap,
координатор и проверку точного SHA перед merge через локальный FakeForge.
Сценарии: PASS; CHANGES → rework → PASS; предел двух rework; падение reviewer;
отмена reviewer; рестарт во время reviewer. Следующий тикет не начинается
до merge, повторный tick не повторяет merge.
`src/runtime/local/recovery-process.test.ts` запускает отдельный процесс-владелец,
подаёт реальные SIGTERM/SIGKILL, проверяет исчезновение агента и его дочернего
процесса, сохранение обновлённых тестовых credentials и восстановление файлов
из bundle. `cancel-cleanup.test.ts` дополнительно проверяет отказ архивирования.
`src/server/main/shutdown.test.ts` проверяет настоящий серверный entrypoint.

Живой smoke-пилот: настоящий Codex `gpt-6.1-sol`, ChatGPT auth, restricted-сеть,
изолированный workspace подключённого **gym-crew**, commit
`3f31b3373e646c1728a517e6195f3651ff5704ed`. Успешно выполнены чтение проекта,
`git rev-parse HEAD` и `git status --short`; runtime завершился с exit 0.
Тесты приложения **не запускались**: отсутствовал `node_modules`, установка
зависимостей не входила в smoke. Изменений, внешнего PR и merge не было.

Границы: это восстановление файлов и авторизации, не продолжение модельной
сессии. Прерванный запуск получает `sandbox_run_lost` либо `cancelled` при
сохранённом запросе отмены; обычные правила координатора действуют дальше.
Игнорируемые Git файлы и staged/unstaged-разделение bundle не сохраняет.
Отказ ОС/питания, принудительное убийство самого контролирующего процесса,
Linux/bwrap и Docker этой проверкой не подтверждены. Инструкции восстановления:
[Codex runtime](codex-runtime.md#остановка-и-восстановление).

### F06.5 P2 Разделить статус выполнения reviewer и результат ревью в UI

Пользователь увидел `succeeded` у reviewer и неожиданный rework. В живом
запуске это означало успешно полученный отчёт `VERDICT: CHANGES` с
`QUALITY_GATE: NOT_RUN`, а не одобрение кода. Координатор правильно запретил
merge и начал rework, но UI не объясняет различие.

**Сделать:** рядом со статусом процесса показывать явный результат ревью
«Пройдено / Нужны изменения / Проверки не выполнены / Ошибка ревью» и причину
перехода к rework. Не превращать корректный CHANGES в технический сбой запуска.
**Готово, когда:** оператор понимает решение без чтения сырого финального
сообщения; сценарии PASS/CHANGES/NOT_RUN покрыты UI-воспроизведением.

Теперь любой завершённый reviewer сверяется с текущим head PR. При изменении

воспроизводят CHANGES до и после завершения доставки, один новый dispatch,
правильный pin и последующее слияние только после нового PASS.

### F08 P2 Правильно определять текущий production-релиз

**Дефект воспроизведён через настоящий handler с подменённым Forge.**
`src/server/handlers/projects.deploy.ts:98–102` ищет успех только среди пяти

**Сделать:** искать текущее развёртывание независимо от длины отображаемой истории;
явно различать неизвестное состояние и отсутствие релиза. Также не запускать
деплой при неудачной проверке активного workflow: сейчас `startProjectDeployHandler`
после `listRuns.ok === false` всё равно вызывает dispatch.
**Готово, когда:** предыдущий рабочий релиз виден после пяти и более неудач;
ошибка чтения workflow не приводит к слепому dispatch. Покрыть handler-тестами
и UI-repro; состояния загрузки/ошибок — S04.

`deploy/docker/Dockerfile.agent` не устанавливает Codex; сквозной проверки

удаление Kubernetes/Jira/Azure, сохранение исходного стека старых проектов,
ожидание владельца после двух неудачных доработок. Это решения исходного плана.
