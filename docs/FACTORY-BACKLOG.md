## Восстановление ревью после отказа запуска (warren-f108)

В плане хоккейного проекта ревью не создало run: в основной ветке отсутствовала
`.warren/config.yaml` с утверждённой командой `qualityGate`. Фабрика скрывала
причину за `The review run did not start` и оставляла активный план без действия
восстановления. Падающий UI repro сохранён в commit `fe646191`.

Ошибка запуска теперь сохраняется с очищенной от credentials причиной. При
отсутствии конфигурации сообщение указывает файл и настройку. Страница плана,
задача и боковая панель Overview/Kanban предлагают Retry review. Действие
повторяет ревью существующего PR на его актуальном SHA; история, лимит доработок,
бюджеты и блокировка следующего тикета сохраняются. Двойное нажатие обрабатывается
под общей блокировкой координатора и не создаёт второй запуск. Активное ревью,
отменённый план и другие задачи не допускают повтор. Проверка качества и политика
слияния продолжают действовать.

Серверные регрессии проверяют отказ до создания reviewer run, повтор после
неудачного reviewer, повторный отказ, сохранение истории, секреты и права доступа.
`repros/warren-f108.pw.ts` проверяет действие на компьютере и телефоне в обеих темах.

фиксируются в приватных отчётах пилота и описании PR, без публикации credentials.

## Overview, Kanban и Production (warren-f105)

Согласованный multi-project workspace реализован в Warren:

- Overview — главная страница, общая очередь вмешательств, до трёх текущих
  задач на проект, последние результаты и отдельный блок Production.
- Kanban — полный список уже созданной работы с поиском и отдельными этапами
  Review, Ready for review, Merged и Production. Старый `/tasks` сохранён
  для существующих ссылок и подробной истории.
- Проект сохраняется между тремя страницами, в URL и после перезагрузки.
  Карточка открывает боковую панель; на телефоне она занимает весь экран.
- Задачи объединяются по проекту и tracker ID либо явным связям
  retry/continuation. Review и rework входят в исходную задачу. Автоматический
  Review и временное ожидание merge не становятся обращениями к владельцу.
- Новая задача создаётся из workspace: проект, результат, затем отдельный
  run или существующий план и агент с defaultRole проекта. План выполняет
  существующие задачи; этот выбор не генерирует новый план.
- В панели доступны сообщения текущему агенту, остановка задачи/плана,
  повторный запуск и продолжение, PR, Preview, Logs, бюджеты и история.
  Проверка и merge PR используют GitHub и действующую политику фабрики.
- Production показывает текущий Release, SHA ветки для следующего Deploy,
  изменения и реальный workflow. Deploy относится ко всему проекту.
  После запроса UI ждёт данных GitHub; таймер не создаёт успешный Release.
  Если workflow завершился между обновлениями, UI показывает его результат
  по ID, снимает ожидание запуска и сохраняет отдельно подтверждённый Release.
  Статус задачи Production требует сохранённого deployment_verified
  после workflow, проверки точного SHA и smoke. Это факт прохождения этапа;
  текущая опубликованная версия показана отдельно на странице Production.

Основная навигация: Overview, Kanban, Production; служебные разделы доступны
через More. Обычные подписи на русском, programming terms сохранены на английском.
Новых зависимостей и изменений схемы БД нет.

Workspace читает историю выбранных проектов из существующих API, включая
постраничный список runs и детали планов. Ошибки помечают снимок как неполный;
при неизвестном состоянии production успех не предполагается. Недиспетчеризованный
backlog остаётся в tracker и доступных планах. Для очень большой истории следующая
оптимизация — серверная пагинация логических задач с сохранением всех связей попыток.

Проверки: `scripts/ui-visual/workspace.pw.ts`, модель группировки задач,
operator/public projections и источник deployment evidence. Матрица браузера
покрывает 393/1440 px, светлую и тёмную темы, реальные HTTP-действия на fixture,
ошибки и восстановление. Изменения API не требуют миграции или перезапуска runs.
Полная браузерная матрица: 389 passed, 1 skipped (goldens только в CI-контейнере).
После исправления быстрого Deploy повторно проверены затронутые страницы;
repro `warren-f105.pw.ts` проходит для success/failure во всех четырёх вариантах.
На живых данных проверено объединение 73 runs в 14 задач с одним реальным
merge blocker; эта проверка выполнялась без dispatch или deploy.

## Рабочий экран: первый этап UX-исправлений (warren-f101)

Реализованы первые три пункта проверки экрана с возобновлённым планом:

1. Одна карточка на задачу трекера в пределах проекта. Старые попытки остаются
   в раскрываемой истории; отменённые попытки не создают ложных требований
   вмешательства. Одновременная работа, блокировки других открытых попыток
   и ранее зафиксированные production-инциденты остаются видимыми.
2. Прогресс показывает позицию текущей задачи и раздельные числа доставленных,
   ранее закрытых, ожидающих и неудачных задач. `skipped` означает закрытие
   в трекере до запуска, а не подтверждённую доставку. Для остановленных
   планов оставшиеся задачи подписаны «не начаты».
3. Текущая работа идёт первой. На карточке и в деталях задачи видны этап,

   свежесть данных и ссылка на его журнал. При переходе к review/rework
   журнал переключается на соответствующее исполнение. Ошибка обновления
   сохраняет последний снимок и предлагает повторить запрос.

История загружается порциями по 12 планов; все активные планы включаются
сразу. Поиск и история попыток ограничены загруженными планами, что указано
рядом с кнопкой загрузки остальных. Данные запусков не удаляются.

Реализованы первые три замечания повторной UX-проверки:

1. Детали открываются с начала страницы. Возврат браузером или ссылками
   «Back to plan», «Back to plans», «All tasks» восстанавливает прежнее место
   в пределах текущей сессии интерфейса. Поиск, фильтры, сортировка и число
   загруженных планов хранятся в адресе списка и переживают его перезагрузку.
2. Карточка, детали задачи, сводка и список планов используют одно представление
   текущего состояния. Отказ автоматического слияния после успешного ревью

   «Merge retry pending». Завершённые и отменённые попытки сохраняют свой статус.
3. Карточка сразу показывает конкретную причину, затронутые файлы и следующий
   шаг. В деталях отказ слияния собран в одно предупреждение; успешный отчёт
   ревью больше не подменяет объяснение блокировки. Причина видна также в
   сводке текущей задачи плана.

Исходные четыре падения сохранены до изменения интерфейса в коммите

правила слияния и частота обновления списка планов не меняются.
Все 24 новых браузерных сценария проходят. Общий прогон: 320 passed,

## Рабочий экран: компактная история и суммы попыток (warren-f104)

Закрыты оставшиеся три пункта повторной UX-проверки:

1. Полные отчёты свёрнуты, включая последний. Последний результат остаётся
   видимым с кратким фрагментом отчёта; весь текст и доказательства раскрываются
   клавиатурой или нажатием. Для реализации, ревью и доработок показаны даты
   начала/окончания и длительность. Идущие шаги показывают растущее время,
   завершённые без даты окончания — неизвестную длительность. Временные данные
   загружаются только для видимых шагов через существующий API запусков.
2. Стоимость плана вынесена перед списком задач, рядом со сводкой прогресса.
   Одна разметка используется на телефоне и компьютере. Расход выбранной
   попытки и сравнение попыток в деталях задачи расположены рядом.
3. Карточка и детали показывают сумму этой задачи по загруженным попыткам,
   включая выбранную ровно один раз. Детали загружают историю проекта порциями
   по 12 планов; недоступные и ещё не загруженные попытки не выдаются за полный
   итог. В каждой попытке используются канонические метрики всей задачи.
   Итоги складываются до округления. Раскрываемый расчёт показывает значения
   с шестью знаками и разницу округления; она не является дополнительным расходом.
   Неизвестные измерения и оценки подписки остаются явно подписанными.

высота последнего отчёта 2247 px, отсутствие дат, стоимость после списка задач
и отсутствие итога по попыткам. Регрессия `scripts/ui-visual/repros/warren-f104.pw.ts`
покрывает раскрытие полного текста, даты, неизвестное время, загрузку только

## Текущее состояние интеграции

F01–F06 исправлены ранее. Живой пилот gym-crew PR #9 прошёл до автоматического
слияния на runtime `48a21af3`. Эта проверка относится к прежней версии цепочки.

В текущем наборе изменений закрыты F06.5, F07, F08 и S01–S05:

- Вердикт reviewer отделён от статуса процесса. Задача открывается как целая
  цепочка реализации, код-ревью, UI-ревью и доработок, с причиной и следующим шагом.
- Подключение имеет рабочую справку и проверки существующего gate. Навыки

- Production ищет активный релиз отдельно от пяти строк истории. Неизвестное
  состояние, загрузка и ошибки видны. Расчёт и dispatch вынесены в домен.
- Общие статусы живут в `src/core/wire.ts`. Guard ловит именованные и анонимные
  копии словарей доставки. Ссылки и инструкции отделяют текущий форк от upstream.

Добавлены подтверждённые требования из прежнего обсуждения:

| Пункт | Реализация и границы |
|---|---|
| Независимый quality gate | Runtime получает реальный exit code в отдельной копии закреплённого коммита. Merge требует машинного свидетельства. Скрипт gate должен сам подготовить зависимости. Это не внешняя неизменяемая спецификация продукта. |
| Рискованные изменения | Обязательные пути, скрипты gate из base-конфига, запрет автоматического merge для симлинков/сабмодулей, binary и большого diff. Подробности: [merge safety](factory-merge-safety.md). |
| Production после merge | Явный opt-in, точный SHA, workflow, активный Deployment, HTTP smoke, инцидент и остановка очереди. Требует подготовленного workflow проекта. Подробности: [production delivery](production-delivery.md). |
| UI/UX-ревью | Отдельный холодный reviewer после код-ревью для UI-файлов. Должен проверить реальный интерфейс и описать полученные доказательства. Не заменяет тесты самого проекта. |
| Контекст | Событие `context.metrics`: UTF-8 bytes по сегментам и явно приблизительные tokens. Это не измерение фактического расхода каждого скилла. |
| Уроки | Идемпотентные `factory.learning` после rework, эскалации, deployment/smoke failures. Содержат наблюдение и источник, без выдуманной причины. Ретроспектива остаётся ручной. |

не входят в этот набор.

## Задачи по поведению

Приоритет **P1** — закрыть до доверенного автоматического слияния;
**P2** — следующая очередь для надёжной повседневной работы;
**P3** — расширение за пределы текущего локального режима.
Идентификаторы ниже локальны для этого списка, это не созданные Seeds/GitHub issues.

### F01 P1 — исправлено: строгий вердикт и статус проверок

Результат PASS принимается только с точной первой строкой и двумя обязательными
полями: `REVIEWED_COMMIT: <40-символьный SHA>` и `QUALITY_GATE: PASS`.
Цитаты, конфликтующие заголовки, старый PASS без полей, FAIL/NOT_RUN и блок
`Not run:` не разрешают слияние. Промпт reviewer требует CHANGES при пропущенной
обязательной проверке. SHA результата сравнивается с сохранённой точкой ревью.

Код: `src/plan-runs/review-result.ts`, `review.ts`,
`src/registry/builtins/factory-roles.ts`. Регрессии: `review-safety.test.ts`,
`review.test.ts`. Это структурированное подтверждение reviewer; независимое
исполнение qualityGate сервером не добавлено. Реальный прогон роли — F06.

### F02 P1 — исправлено: слияние проверенного коммита и общая политика

SHA читается до запуска reviewer, сохраняется в событии и используется как
`baseCommit` его workspace. Если вершина PR изменилась, начинается новое ревью.
GitHub merge получает обязательный `sha`, поэтому push между проверкой и записью
merge отклоняется сервером GitHub. Ответ без `merged: true` не считается успехом.

Merge-on-PASS использует существующую политику `decideAutoMerge`: конфиг берётся
из удалённой базовой ветки, diff — из отдельного git snapshot; защищённые пути,
изменение `.warren/config.yaml` и непрочитанный diff запрещают merge. Старый reap
не включает auto-merge для implementer до независимого ревью.

Код: `src/plan-runs/review-forge.ts`, `src/runs/reap/auto-merge-arm.ts`,
`auto-merge-snapshot.ts`, `src/forge/github/provider.ts`.
Тесты: `review-forge.test.ts`, `src/forge/github/review-safety.test.ts`,
`auto-merge-arm.test.ts` и существующие snapshot/policy-тесты.

**Настройка:** для автоматического слияния нужны и
`WARREN_PLAN_RUN_MERGE_ON_PASS=1`, и `pr.autoMerge` в базовой ветке проекта.
Один глобальный флаг больше не обходит политику проекта. Самостоятельный
implementer вне plan-run требует ручного слияния: независимого review-step
в таком запуске нет.

### F03 P1 — исправлено: отмена активного review/rework

Отмена проверяет связанные review/rework-запуски и исходный implementer,
передаёт cancel активному runtime и не называет завершённый run отменённым.
Общий lock сериализует отмену и переходы координатора: после завершённой отмены
следующий шаг не стартует. Повторный cancel уже отменённого плана повторяет
незавершённую остановку, если первый запрос к runtime завершился ошибкой.

Код: `src/plan-runs/cancel.ts`, `lock.ts`, `coordinator.ts`.
Тесты: `cancel.test.ts`, `review-safety.test.ts` — review, rework, гонка spawn/cancel,
повтор после transport failure и освобождение счётчика после reap.
Остановка процесса и освобождение реального auth lease остаются частью F06.
При недоступном runtime ошибка логируется; требуется повторить cancel после
восстановления связи, автоматического фонового повтора cancel пока нет.

### F04 P1 — исправлено: восстановление шагов и доставки результата

Вердикт, попытки merge, подтверждение merge, попытки публикации и завершение
записываются отдельно. `review_finished` появляется после доставки либо
исчерпания лимита. Merge и комментарий имеют по три попытки; исчерпание отмечается
как `broken` и `needs_attention`, причина остаётся в событии.
После сбоя между merge и комментарием координатор завершает доставку, прежде чем
перейти к следующему тикету. Слитый SHA распознаётся без повторной записи merge.

Комментарий имеет стабильный маркер; перед повтором GitHub проверяется на уже
опубликованный отчёт, включая страницы истории. Слепые HTTP-повторы POST выключены.
Связь с review/rework сохраняется в callback после создания строки run, но до
вызова runtime. Ошибка callback завершает строку как `never_started` и не создаёт
sandbox. Перезапуск продолжает работу по событиям и не порождает второй reviewer.

Код: `src/plan-runs/review-delivery.ts`, `review.ts`, `in-flight.ts`,
`src/forge/github/review-comment.ts`, `src/runs/spawn/dispatch.ts`.
Тесты: `review-safety.test.ts`, `src/forge/github/review-safety.test.ts`,
`src/runs/spawn/admission.test.ts`.

Старые записи `review_finished`, созданные прежней версией, автоматически
не переигрываются: их PR нужно проверить вручную. Аварийная остановка живого
процесса и восстановление workspace проверяются отдельно в F06.

### F05 P1 — исправлено: общее ограничение запуска

Все пути через `spawnRun` резервируют слот до clone/runtime работы и учитывают
все незавершённые runs, включая ручные. Резерв заменяется строкой БД под общей
синхронизацией; тест со специально задержанным чтением проверяет эту гонку.
Ручной запрос получает понятный отказ до создания sandbox; план остаётся ждать,
а cron не расходует попытки и не теряет текущую задачу из-за занятого слота.

Лимит по умолчанию — один. Существующее имя env
`WARREN_AUTOMATIC_MAX_CONCURRENT_RUNS` сохранено, но теперь охватывает все
запуски. Окно `WARREN_AUTOMATIC_RUN_WINDOW` по-прежнему относится только к
автоматическому расписанию. Синхронизация рассчитана на один сервер-владелец БД.

Код: `src/runs/spawn/admission.ts`, `src/triggers/automatic-capacity.ts`,
`dispatch.ts`, `src/plan-runs/tick.ts`. Тесты: `admission.test.ts`,
`admission-race.test.ts`, `clone-lock.test.ts`, `automatic-capacity.test.ts`,
`dispatch.bounded-retry.test.ts`.

### F06 P1 Сквозная проверка новой цепочки и безопасной остановки

**Локальная часть исправлена и проверена на macOS, 2026-11-10.** Полный внешний
пилот с GitHub также завершён, доказательства — в F06.1 ниже.

Исправлены подтверждённые дефекты:

- `cancel()` и повторная отмена дожидаются завершения drive-loop и сохранения
  credentials. Штатная остановка закрывает все локальные jobs; серверный
  entrypoint обрабатывает SIGINT/SIGTERM через `stop()`.
- На macOS отдельный контролирующий процесс останавливает группу процессов
  песочницы при потере IPC-соединения с сервером, в том числе после SIGKILL.
- До удаления прерванного или грязного workspace сохраняется автономный Git
  bundle: коммиты, изменения отслеживаемых файлов и новые неигнорируемые файлы.
  Это действует и при boot-reconcile, и при GC. Ошибка сохранения оставляет
  workspace на месте; путь bundle доступен в событии удаления и, для reap и
  boot-reconcile, в `salvagePath` запуска.
- Журнал вне HOME позволяет сохранить обновлённые Codex credentials после
  рестарта. Ошибка записи исходного auth-файла сохраняет временный файл и
  журнал для повторного восстановления. Manifest записывается атомарно;
  runtime не запускается, если сохранить manifest не удалось.
- Отдельный `runtime_event_seq` в SQLite/Postgres отделяет курсор runtime от
  служебных событий плана. Раньше короткий запуск мог потерять свой итоговый
  ответ и остаться `queued`; сквозной тест воспроизвёл это зависание.
- Потерянные reviewer/rework не получают отдельный автоматический retry вне
  координатора плана. Ревью после потери runtime требует внимания владельца.
