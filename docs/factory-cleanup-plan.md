# Упрощение фабрики: запуск на текущем Mac

Итоговый план от 14 ноября 2026 года. Решения согласованы владельцем;
план готов к исполнению, реализация не начата.
Проверка исходников: `93e39640a0bfd0e60fff575b48fa6bbb528ccf0a`.
Термины: [GLOSSARY.md](../GLOSSARY.md).

Спецификация эпика: [простая автономная фабрика](factory-redesign-spec.md),
метка `ready-for-agent` в проектной очереди.

Уточнение владельца от 14 ноября: сейчас всё исполнение фабрики остаётся на этом
устройстве. Развёртывание на VPS и перенос очереди отложены; сохраняется только
архитектурный задел. Этапы и приёмка ниже обновлены под локальный запуск.

Этот документ задаёт порядок переделки личной фабрики. [PLAN.md](PLAN.md)
сохраняет предыдущий план и историю. [FACTORY-BACKLOG.md](FACTORY-BACKLOG.md)
фиксирует фактическое выполнение этапов; перечисленные здесь возможности
не считаются поставленными до прохождения соответствующей приёмки.

## Цель

Владелец согласует план, запускает его один раз и получает проверенный результат
с deploy без ручного ремонта каждого шага. Фабрика и её интерфейс работают
на текущем Mac. Deploy приложений проектов остаётся частью цикла; размещение
самой фабрики на сервере сейчас не выполняется.

## Подтверждено в текущем интервью

- Один координатор на текущем Mac. Закрытие вкладки не отменяет работу;
  выключение или сон устройства не позволяют обещать непрерывное исполнение.
  После возобновления фабрика сверяет незавершённые действия.
- На первом этапе используется Codex CLI. По словам владельца, Codex CLI и
  Claude Code уже установлены и авторизованы на VPS. Эта сессия сервер не проверяла.
- Claude Code пока не подключать; существующие установку и настройки не менять.
  Возможность последующего выбора Codex или Claude Code сохранить.
- Выбор исполнителя и модели должен работать через интерфейс без SSH и правок кода.
- Один источник навыков и MCP для Codex, Claude Code и фабрики, включая разработку
  самой фабрики. Допустимы копии или генерация файлов нужного агенту формата.
- Задачи выполняются без системной песочницы, под учётной записью локального запуска.
  Отдельные рабочие копии, отмена и таймауты сохраняются.
- Ревью и проверки проходят для каждой задачи. Deploy выполняется в конце плана
  или на явно отмеченном этапе.
- Обычный код, зависимости и сборка проходят автоматически. Изменения прав доступа,
  разрушительные миграции и правил самой фабрики требуют отдельного решения,
  если конкретные изменения не были явно одобрены в плане.
- Основная навигация: Задачи, Проекты, Настройки. Планы, опубликованная версия
  и состояние deploy находятся внутри проекта. В карточке задачи сразу видны
  цель, текущий этап, проверенный результат и требуемое действие. Технические
  разделы убираются из обычной навигации; диагностика открывается отдельным действием.
- Из поддерживаемого продукта убираются Pi, Docker-исполнение, автоматические
  патрули и отдельные расширения judge/campaign-controller. Общие функции,
  нужные основной цепочке, сохраняются; удаление идёт по проверенным зависимостям.
  Обычное исполнение на Mac и адаптер Claude Code сохраняются; Linux остаётся
  будущей целью переносимости, без требования живого развёртывания сейчас.
- В проекте отдельно выбираются исполнитель и ревьюер: CLI и модель для каждого.
  План запоминает настройки при старте. Изменения настроек применяются к новым
  планам; автоматического перехода к другому исполнителю при ошибке нет.
  Сейчас доступен Codex, Claude Code появится после отдельного подключения.
- Начальные лимиты: две попытки восстановления окружения; до трёх доработок
  после ревью при подтверждённом прогрессе; 60 минут на запуск и три часа активной
  работы на задачу, включая подготовку и проверки. Ожидание внешней проверки
  учитывается отдельно, максимум час на этап. Лимиты доступны в настройках проекта.
  Исчерпание бюджета останавливает затронутый проект, не остальные проекты.
- После неуспешной проверки deploy фабрика возвращает последнюю проверенную
  версию, проверяет восстановление и направляет изменение на исправление в пределах
  оставшегося бюджета. Следующие этапы проекта ждут. Если результат deploy неизвестен
  или возврат требует обратного изменения данных, сначала выясняется состояние;
  невозможность подтвердить безопасное восстановление останавливает проект с причиной.
- При старте сохраняется версия согласованного плана: задачи, ожидаемые результаты,
  обязательные проверки, границы релизов, разрешённые особые изменения и исполнители.
  Изменения тикетов и новые пожелания не подхватываются автоматически: владелец
  согласует их и применяет к оставшейся работе отдельным действием в интерфейсе.
- Общий набор включает навыки Pocock/pstack, Context7, Playwright, Exa и локальный
  Graphify. Обязательное условие владельца: бесплатное использование инструментов,
  без дополнительных платных подписок, API и автоматического перехода на оплату.
  Существующая авторизация модельных исполнителей — отдельная часть настройки.
- Подключение через интерфейс: репозиторий или новый проект. Готовность окружения,
  проверок, прав, merge и deploy обязательна до допуска автономного плана.
  Первые рецепты: Python/uv, JavaScript/TypeScript с менеджером проекта и Go;
  другие стеки — через заданные команды. Существующий стек сохраняется,
  новый согласуется до создания проекта. Настройки репозитория оформляются одним PR.
- Seeds сохраняется как внутренний механизм задач и планов без ручной работы с CLI.
  Mulch — опция, выключенная для новых проектов; существующая память сохраняется.
  Внешние трекеры и расширения audit-log/tracker-conformance убираются из продукта.
  Встроенные история, диагностика и необходимые проверки сохраняются.
- Интерфейс и API локальны, действующая защита доступа сохраняется; публикация
  сервера в сеть не нужна. Перед обновлением сохраняются история и очередь,
  завершается активная работа, создаётся копия и проверяется восстановление.
  Удалённый HTTPS, служба VPS и внешнее резервирование сервера отложены вместе
  с переездом. Существующие установки на VPS не изменяются.
- Приёмка сначала на тестовом проекте: изменение зависимости, проверка интерфейса,
  сбой подготовки, рестарт фабрики, неудачный deploy с восстановлением. Затем аудит
  доставки хоккейного проекта и согласованная небольшая задача. Успех требует
  проверенного приложения, подтверждённой версии и понятного результата в карточке.
- При исчерпании бесплатной квоты используются доступные исходники, локальные
  инструменты и документация. Работа продолжается только при достаточных основаниях
  и выполнении обязательных проверок. Иначе останавливается затронутая задача
  с объяснением; платные подключения не включаются и проверки не пропускаются.
- При подключении проекта задаются три доказательства успешного deploy:
  нужная версия опубликована, приложение отвечает, основной пользовательский
  сценарий работает. Проверка безопасна для рабочих данных. Те же доказательства
  требуются после отката; одного успешного HTTP-ответа недостаточно.

## Состав очистки

Направление удаления Pi, Docker-исполнения, автоматических патрулей, внешних
трекеров и четырёх отдельных расширений согласовано. Общие функции сохраняются
по зависимостям. Удаление кода не должно удалять историю прежних запусков.

- Устаревшие утверждения о Kubernetes, Burrow и Canopy; противоречащие коду
  инструкции по merge, лимитам и месту размещения фабрики.
- Старые точки входа контейнерного исполнения. Часть общих функций ещё используется
  HTTP-обработчиками, поэтому удалению предшествует разбор зависимостей.
- Pi, Docker-исполнение, автоматические патрули и judge/campaign-controller
  удаляются с сохранением функций, нужных основной цепочке. Работающие установки
  Claude Code на машине владельца и VPS это решение не затрагивает.
- Внешние трекеры, audit-log и tracker-conformance удаляются из поддерживаемого
  продукта. Seeds сохраняется внутри основной цепочки. Mulch остаётся опцией
  проекта с сохранением существующей памяти.
- В интерфейсе убрать свободный ввод несовместимых сочетаний провайдера и модели,
  технические сущности из основной карточки и дублирующие способы просмотра работы.
  Видимые разделы ограничены согласованными Задачами, Проектами и Настройками.

## Порядок работ

Этапы выполняются по порядку. Каждый заканчивается проверяемым результатом;
ошибка приёмки не переносится в следующий этап как скрытая ручная работа.
Код готовится отдельными небольшими изменениями. Рабочая установка обновляется
только на этапе 9, после локальной проверки новой фабрики на тестовом проекте.
Переноса очереди на другую машину в этом плане исполнения нет.

| Этап | Результат | Главный критерий выхода |
|---|---|---|
| 1. Исходное состояние | Карта удаления, состояния и зависимостей | Известно, что сохраняем и что нельзя потерять |
| 2. Очистка | Поддерживается согласованный состав продукта | Основная цепочка и история работают после удаления лишнего |
| 3. Исполнение и окружение | Обычные процессы на Mac, автоматическая подготовка | Агент и независимая проверка работают из чистых копий |
| 4. Инструментарий и профили | Один набор навыков/MCP, отдельные исполнитель и ревьюер | Проверены бесплатный режим и настройки реального запуска |
| 5. Выполнение плана | Согласованный снимок, бюджеты и восстановление | Рестарт и повтор не теряют работу и не дублируют действия |
| 6. Подключение и доставка | Проверка готовности, границы релиза и rollback | Неверная версия и сломанное приложение не получают успех |
| 7. Простой интерфейс | Задачи, Проекты, Настройки | Полный рабочий сценарий доступен без SSH и ручного YAML |
| 8. Локальная тестовая приёмка | Отдельное состояние, резервная копия, проверенный полный цикл | Проходят обычные задачи и искусственные сбои |
| 9. Обновление и пилот | Один рабочий координатор на текущем Mac | История сохранена, хоккейный проект доставлен и проверен |

### 1. Зафиксировать исходное состояние

Работа: сверить HEAD и изменения после исходного аудита; составить карту удаляемых
модулей, их потребителей и совместимости исторических данных. Без изменения
работы инвентаризировать текущий Mac: процессы, очередь, историю, рабочие копии,
неотправленную Git-работу и незавершённые merge/deploy. Проверить ОС, ресурсы,
учётную запись запуска, доступность Codex и место резервной копии.
Способ резервирования выбрать по фактически доступному хранилищу. VPS не проверять
и не изменять в рамках этого этапа.

Приёмка:

- Для каждого удаления известны потребители и сохраняемые общие функции.
- Перечислены данные и внешние действия, требующие сохранения либо сверки.
- Проверена возможность запустить Codex локально без изменения
  Claude Code. Секреты и приватные адреса находятся вне публичных документов.
- Неизвестные факты записаны как препятствия конкретного этапа. Новые расходы
  и разрушительные действия не считаются автоматически разрешёнными.

### 2. Удалить согласованное лишнее

Работа: удалить Pi, Docker-исполнение, автоматические патрули, внешние трекеры
и четыре расширения. Общую логику старых контейнерных точек входа сначала
перенести к актуальному владельцу. Сохранить адаптеры Codex/Claude Code, Seeds,
опциональную память, управление процессами, ревью, проверки, историю и Git-доставку.
Убрать устаревшие зависимости, команды установки и активные инструкции.

Приёмка:

- Установка и запуск не требуют удалённых компонентов.
- Исторические запуски читаются с прежними идентификаторами и исходами;
  удалённые исполнители недоступны для новых запусков.
- Существующие проверки основной цепочки проходят. Удаление теста допустимо
  только вместе с удалением его функции, а не для скрытия регрессии.
- Для удаляемых публичных путей docs добавлены указатели в docs/README.md.
  Документация различает текущую реализацию и ещё не поставленные этапы.

### 3. Подготовить обычное исполнение и окружение проекта

Работа: заменить системную песочницу обычным локальным запуском на Mac.
Сохранить отдельные рабочие копии и настройки каждого запуска, управление деревом
процессов, отмену, таймауты и сохранение Git-работы. Убрать предположения о путях
внутри песочницы. Добавить версии toolchain и команду подготовки проекта.
Подготовка выполняется перед агентом и перед независимой проверкой закреплённого
коммита. Повторно используются кеши скачивания, а не произвольные node_modules.

Приёмка:

- На Mac агент запускается, завершается и отменяется без зависших дочерних
  процессов. Лимиты охватывают подготовку и проверку, а не только модельный процесс.
- Чистые Python/uv, JavaScript/TypeScript и Go проекты готовятся по своим lockfile
  и версиям. Неизвестный стек допускается через явный рецепт без смены стека.
- Независимая проверка не использует незакоммиченные файлы и установленные агентом
  зависимости из его копии. Изменение проверяемых исходников обнаруживается.
- Сбой подготовки имеет отдельную причину и ограниченный повтор; ошибки кода
  не маскируются переустановкой окружения.
- Корни данных и пути исполняемых файлов настраиваются; платформенные особенности
  остаются за существующей границей runtime. Поддержка будущего Linux не требует
  сейчас установки на сервер или заявления о проверенном Linux-исполнении.

### 4. Собрать общий инструментарий и профили

Работа: один каталог, версии источников и генерация конфигурации для Codex/Claude
Code на Mac, с переносимым каталогом для будущего VPS. Устранить конфликтующие имена и инструкции навыков,
сохранив их зависимости. Подключить Context7, Exa, локальный Graphify и Playwright
в бесплатном режиме. Разделить роль, CLI-исполнителя и модель; хранить отдельные
профили реализации и ревью с настройкой через серверный API, затем интерфейс.

Приёмка:

- Личная сессия и запуск фабрики получают одну версию каталога. Повторная доставка
  не создаёт дубли и не стирает посторонние настройки. Нет токенов и истории сессий
  в общем пакете. Конфигурация Claude Code на VPS остаётся неизменной.
- В настоящем запуске работают поиск Exa, документация Context7, браузер Playwright
  и запрос к локальному графу. Граф привязан к текущей копии и обновляется после
  изменения кода. Результаты Graphify подтверждаются исходниками и проверками.
- Нет вызовов платных backend и скрытого запуска Claude Code. Исчерпание квоты
  моделируется: обязательная проверка не пропускается, оплата не включается.
- Несовместимые CLI/модель отвергаются до запуска. Модель ревью выбирается отдельно;
  доработка использует профиль реализации. Автоматического fallback исполнителя нет.
- Обновление набора не меняет действующий план; новая версия проверяется перед
  применением к новым планам. Откат версии пакета не требует ручной сборки настроек.

### 5. Сделать выполнение плана воспроизводимым

Работа: сохранять снимок задач, условий приёмки, границ релиза, разрешений,
профилей и версии инструментов. Записывать этапы и попытки до внешних действий;
после рестарта сверять фактический результат перед продолжением. Сохранить
реализация → независимое ревью → доработка → проверка → merge, независимо
от выбранного CLI. Изменение имени роли не должно обходить обязательное ревью.

Приёмка:

- Правка тикета, настроек проекта или набора навыков не меняет запущенный план.
  Явное изменение оставшейся работы сохраняет предыдущую версию и решение владельца.
- Отмена не вызывает автоматический повтор. Рестарт не обнуляет бюджет; восстановление
  относится также к ревью и доработке. Потеря модельной сессии не объявляется её
  успешным продолжением: сохраняется работа и создаётся связанная попытка.
- Повторный запрос и рестарт возле создания PR/merge не создают дубликаты.
  Состояние с неизвестным внешним исходом сначала сверяется с площадкой.
- Действуют две попытки ремонта, три доработки при прогрессе, 60 минут на запуск,
  три часа активной работы на задачу и час ожидания внешней проверки на этап.
  Есть одна причина остановки и следующее действие; другие проекты могут работать.
- Прогресс подтверждается устранением прежнего воспроизводимого дефекта или
  прохождением ранее падавшей обязательной проверки. Повтор прежнего отказа
  без новых доказательств не продлевает цикл. Смена формулировки ревью не прогресс.
- Merge относится к проверенному SHA и актуальной базе. Обязательные CI-проверки
  и действующие ограничения сохраняются. Обычный код, lockfile и сборка проходят
  без лишнего запроса; особые изменения сверяются с явными разрешениями плана.

### 6. Подключать готовые проекты и проверять доставку

Работа: подготовить единый результат проверки готовности проекта и API подключения
существующего репозитория/создания нового. Настройки и необходимые изменения workflow
предлагать одним PR, сохраняя работающую схему deploy. Добавить границы релиза:
обычный merge задачи не вызывает deploy; выпуск происходит в конце плана или этапа.
Реализовать проверку версии, доступности и пользовательского сценария, rollback
и хранение последней проверенной версии.

Приёмка:

- Все недостающие условия видны одной сводкой. Пока подготовка, проверки, права,
  merge или доставка не готовы, автономный запуск отклоняется с точными причинами.
  Повторная настройка не плодит проекты и PR; существенные изменения инвалидируют
  прежнее доказательство готовности.
- Новый проект получает согласованный стек и те же проверки готовности.
  Seeds обслуживается фабрикой; Mulch по умолчанию выключен в новом проекте.
- Для плана из нескольких задач выполняется один выпуск на объявленной границе.
  Задача после merge показывает ожидание выпуска; план успешен только после
  проверки всех обязательных выпусков. Необъявленных промежуточных deploy нет.
- Не тот SHA, HTTP 200 с неработающим сценарием и незавершённый workflow не дают
  статус успешного выпуска. Сведения площадки и работающего приложения согласованы.
- Неудачный выпуск возвращает последнюю проверенную версию и проверяет её теми же
  условиями. Исправление получает связанный PR и проходит полную цепочку снова.
- Автоматический rollback допускается только при подтверждённой совместимости
  предыдущего приложения с текущими данными. Деструктивная миграция, отсутствие
  предыдущей проверенной версии или невозможность проверить восстановление
  останавливают проект с причиной, без выдуманного успешного отката.
- Неоднозначный dispatch сначала сверяется с площадкой. Новое выполнение не
  стартует, пока неизвестно, чем закончилась предыдущая попытка публикации.

### 7. Собрать простой рабочий интерфейс

Работа: оставить Задачи, Проекты и Настройки. Объединить представления задач;
попытки реализации, ревью и доработки показывать внутри одной задачи. Планы и
выпуски расположить в проекте, техническую диагностику открывать отдельным действием.
Вывести название результата и понятное описание вместо первой строки сырого промпта.
Подключение проекта, профили, лимиты, запуск, остановка и восстановление доступны в UI.

Приёмка:

- В обычной навигации нет Runs, Events, Telemetry, Operations, Agents и секции
  More с прежней консолью. Неиспользуемые возможности вообще не показываются.
- Карточка отвечает: что хотели получить, что происходит, что проверено и
  опубликовано, требуется ли действие владельца. Описание видно без поиска в логах.
  Краткий результат связан с доказательствами; при отсутствии данных успех не выдумывается.
- Реализация, ревью и повтор не превращаются в три несвязанные задачи.
  Есть состояния ожидания выпуска, успешного rollback, остановки и недостатка данных.
- Через UI можно подключить проект, выбрать разные профили реализации/ревью,
  согласовать и запустить план, посмотреть результат и выполнить допустимое
  восстановление без SSH, YAML или редактирования фабрики.
- Пустые, загружаемые и ошибочные состояния работают на 393px и 1440px в обеих
  темах. Пройдены smoke, axe и воспроизведения UI-дефектов; эталоны с ноутбука
  не перегенерируются. Старые ссылки ведут к задаче или диагностике без потери истории.

### 8. Проверить новую фабрику локально

Работа: запустить новую версию на текущем Mac с отдельным тестовым состоянием
и тестовым проектом. Проверить полный цикл, сбои, сохранение локальной защиты
API и восстановление резервной копии. Проверить обновление самой фабрики
с завершением активных запусков, без обращения к VPS.

Приёмка:

- Локальный интерфейс работает; защита API не ослаблена и сервер не опубликован
  в сеть. Закрытие вкладки не останавливает план.
- После перезапуска локальная фабрика видит прежнюю историю и сверяет
  незавершённые действия. Одновременный второй владелец той же очереди не допускается.
- Последовательный тестовый план включает обычный код, изменение зависимости
  и UI. Получен проверенный выпуск без ручного ремонта окружения.
- Искусственные сбой подготовки, отказ ревью, исчерпание квоты, рестарт во время
  работы, неоднозначный deploy и неуспешный пользовательский сценарий дают
  предусмотренное восстановление либо объяснимую остановку затронутого проекта.
- Восстановление из резервной копии проверено в отдельном месте; восстановленная
  тестовая копия не исполняет рабочую очередь. Обновление/откат фабрики учитывает
  совместимость схемы БД; слепой возврат старого бинарника не считается восстановлением.
- Собраны доказательства без секретов: версии, SHA, попытки, результаты проверок,
  merge, выпуск, rollback, время, токены и ручные вмешательства.

### 9. Обновить локальную установку и провести пилот

Работа: запретить новые старты, завершить активную работу, сверить открытые
PR/merge/deploy и сделать согласованную резервную копию. Обновить локальную
фабрику с сохранением базы, истории, планов, рабочих копий, Git-работы и сведений
о публикациях. Запустить новый процесс только после проверки состояния
и остановки прежнего. Затем провести аудит хоккейного проекта и малую пилотную
задачу. Данные остаются на Mac; перенос на VPS не выполняется.

Приёмка:

- Совпадают состав проектов, история, открытая очередь и связь задач с PR;
  нет потерянной неотправленной работы и повторно выполненных задач.
- Прежняя версия не исполняет очередь одновременно с новой. Возврат на неё
  возможен лишь после остановки новой и сверки новых действий и данных;
  устаревшую копию нельзя запустить параллельно как аварийный вариант.
- Проверены локальный интерфейс и повторное подключение к той же истории.
  Закрытие вкладки не прерывает пилот. Установка и конфигурация VPS не изменены.
- В хоккейном проекте сначала подтверждены текущий выпуск и работающая схема
  доставки, затем выполнена согласованная малая задача до проверенного deploy.
  Искусственные аварии проверяются на тестовом окружении, не в рабочем production.
- Владелец видит понятный результат пилота в карточке. Все обычные шаги прошли
  без ручного ремонта. Любое вмешательство записано; скрытое вмешательство
  не позволяет объявить автономную приёмку успешной.

## Проверки и завершение этапов

Во время реализации используются целевые тесты. Перед фиксацией финальных изменений
проходит `bun run check:all --bail` по правилам AGENTS.md, без повторного широкого
запуска на неизменных входах. Для UI дополнительно выполняется
`bun run check:ui-visual --build`. Исправление UI-дефекта начинается с падающего
воспроизведения и отдельных red/green commits по правилам репозитория.

У каждого этапа в FACTORY-BACKLOG.md фиксируются коммит/PR, проверенные сценарии,
ссылки на доказательства и оставшиеся препятствия. Приватные доказательства
пилота хранятся отдельно; публичный отчёт не содержит адресов, credentials и логов
частных проектов. Красная проверка означает незавершённый этап.

План завершён после этапа 9: рабочая очередь и исполнение остаются на текущем Mac,
согласованный план проходит до проверенного приложения, а заявленные отказы
приводят к проверенному восстановлению или понятной ограниченной остановке.

## Общий инструментарий и подключение — согласованный состав

- Один версионируемый каталог навыков и MCP в репозитории фабрики. Генерация
  настроек для нужного агента и машины; одно имя навыка имеет один источник.
  Общий каталог допускает разное применение навыков: интерактивное интервью
  не должно требовать ответа человека внутри автоматического запуска.
- Основной набор: постановка и планирование, диагностика, проектирование кода,
  тестирование, ревью, инструкции по языкам. Существующие Pocock/pstack сверить
  по именам, зависимостям и совместимости с агентом перед публикацией общей версии.
- Context7 используется для документации. Для браузера сохраняются проверяемые
  Playwright-тесты; первоначально агент получает CLI с навыком, MCP подключается
  при необходимости постоянной интерактивной сессии. Microsoft описывает различие в
  [официальном руководстве](https://playwright.dev/mcp/introduction).
  Context7 поддерживает оба способа доступа согласно
  [официальному README](https://github.com/upstash/context7).
  Exa включается как общий веб-поиск, Graphify — как локальный граф кода.
  При подготовке проверяются поиск в реальном запуске и соответствие графа
  текущей рабочей копии. Оба инструмента включаются при соблюдении условия
  бесплатного использования. Источники:
  [Exa MCP](https://github.com/exa-labs/exa-mcp-server),
  [локальный Graphify](https://github.com/Graphify-Labs/graphify).
- Обновления набора проходят проверку и явно применяются к новым планам;
  активный план сохраняет свою версию. Секреты остаются вне общего репозитория.
  Закрепление клиента удалённого MCP не закрепляет поведение внешнего сервиса.
- Подключение через интерфейс: URL существующего проекта или идея нового.
  Готовность проверяется до допуска плана, результат виден одной сводкой.
  Первые рецепты: Python/uv, JavaScript/TypeScript с менеджером проекта и Go;
  другие стеки используют заданные команды подготовки и проверки.
- Будущий переезд отложен. Для него сохраняются настраиваемые пути, стабильные
  идентификаторы данных, разделение UI/API и граница платформенного runtime.
  Linux-установка, HTTPS на VPS и перенос данных не входят в текущую приёмку.

## Бесплатный режим инструментов

Проверка публичной документации 14 ноября 2026 года подтверждает следующие
варианты. Установка, доступность из реального запуска и квоты этой сессией не проверялись.

| Инструмент | Режим без дополнительной оплаты | Ограничение |
|---|---|---|
| Exa | Анонимный MCP, только поиск и чтение страниц, без ключей и OAuth | Бесплатные лимиты; доступность проверяется из локального запуска |
| Context7 | Анонимный MCP без ключа | Более низкая бесплатная квота; исчерпание не разрешает переход на оплату |
| Graphify | Локальное извлечение только кода, явно `GRAPHIFY_BACKEND=none` | Без семантической обработки документов и вызовов дополнительных моделей |
| Playwright | Локальные CLI/навык и MCP по потребности | Использует ресурсы машины, отдельная подписка не нужна |

Graphify должен оставаться в режиме без модельных backend при каждом вызове,
чтобы не использовать даже установленный и авторизованный Claude Code как fallback.
Exa `agent_run` не входит в бесплатный профиль. Ключи платных сервисов не наследуются
как способ обойти недоступность или исчерпание квоты.

Источники: [Exa MCP](https://exa.ai/docs/get-started/exa-mcp),
[Context7 API](https://context7.com/docs/api-guide),
[Graphify backend](https://docs.graphify.com/open-source/configuration/llm-providers),
[Playwright CLI](https://github.com/microsoft/playwright-cli).

## Факты, которые проверяются при исполнении

Интервью по границам продукта завершено. Начало этапа 1 не требует нового выбора
архитектуры. На нём выясняются состояние текущего Mac, доступность CLI
и бесплатных MCP, активная очередь и место локальных резервных копий.
Для каждого проекта уточняются работающий deploy, контрольный пользовательский
сценарий и доказательство совместимости данных для rollback.

Если факт не подтверждается, останавливается зависимая часть работ с конкретной
причиной. Новая платная услуга, изменение согласованного состава или разрушительное
действие вне согласованного плана требуют отдельного решения владельца.

Развёртывание фабрики на VPS, её удалённый HTTPS-доступ и межмашинный перенос
вынесены за текущий объём работ. Возврат к ним требует новой команды владельца.

Исходный приложенный документ использован как материал для обсуждения.
Утверждения о прежних согласованиях не подменяют ответы текущего интервью.
VPS, production и действующая очередь этой сессией не проверялись и не менялись.
