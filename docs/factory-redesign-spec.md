# Спецификация: простая автономная фабрика на рабочем устройстве

Тип: epic. Метка: `ready-for-agent`. Дата: 14 ноября 2026 года.
Состояние: спецификация готова к реализации; реализация не начата.

Последнее решение владельца: текущий запуск и приёмка выполняются на этом Mac.
Развёртывание фабрики на VPS и перенос очереди отложены. Сохраняется архитектурный
задел для будущего переезда; это не требование текущей приёмки.

## Problem Statement

Владелец хочет один раз согласовать план и получить проверенный выпуск приложения.
Сейчас ему приходится разбираться в технических сущностях, исправлять окружение,
выяснять причины остановок и вручную связывать реализацию, ревью и доставку.
Разные экраны показывают разный состав задач, описания спрятаны, а результат
невозможно уверенно понять по карточке.

Фабрика содержит функции прежнего продукта, которые не нужны выбранному сценарию.
Её текущая проверенная установка связана с Mac, настройки исполнителей и инструментов
разрозненны, готовность подключаемого проекта не подтверждается полным циклом.
После сбоя или перезапуска сохранённая работа не всегда превращается в продолжение
задачи. Успешный HTTP-ответ приложения ещё не доказывает правильность выпуска.

Владелец хочет управлять несколькими проектами и запускать фабрику на текущем Mac,
сохранив возможность будущего переноса на VPS. Он не должен обслуживать набор независимых
конфигураций, платить дополнительно за MCP или подключаться по SSH для обычной работы.

## Solution

Оставить одну фабрику с интерфейсом «Задачи, Проекты, Настройки» и последовательным
выполнением согласованного плана до проверенного выпуска. Обычная работа проходит
через реализацию, независимое ревью, доработку, машинные проверки, merge и deploy
без повторного разрешения на каждый шаг. Особые изменения исполняются только
в пределах конкретных разрешений владельца.

Выполнение происходит обычными процессами на текущем Mac, без системной песочницы,
с отдельными рабочими копиями, подготовкой окружения и лимитами. Mac одновременно
исполняет фабрику и предоставляет интерфейс владельцу. Закрытие вкладки не отменяет
план; выключение или сон самого устройства не позволяют обещать непрерывное исполнение.
После возобновления фабрика выясняет исход незавершённых действий.

Исполнитель и ревьюер выбираются отдельно вместе с моделями. Первый рабочий профиль
использует Codex; архитектура сохраняет Claude Code для последующего подключения.
Единый версионируемый общий инструментарий обслуживает личные сессии и фабрику.
В него входят навыки Pocock/pstack, Context7, Exa, локальный Graphify и Playwright
без дополнительных платных подписок или API.

Проект допускается к автономному исполнению после проверки готовности. Публикация
происходит на границе релиза, по умолчанию в конце плана. Проверенный выпуск
подтверждает нужную версию, доступность приложения и пользовательский сценарий.
Неудача приводит к проверенному безопасному откату либо понятной остановке проекта.

## Implementation Decisions

1. Сохраняются существующие координатор планов, доменные операции проектов и запусков, Git-доставка, ревью, независимые проверки и адаптеры исполнителей. Изменения выполняются постепенно, без второго параллельного ядра фабрики.
2. Один локальный координатор владеет рабочей очередью на текущем Mac. Интерфейс обращается к локальному API; удалённый HTTPS-вход, установка службы на VPS и перенос очереди не выполняются. Граница UI/API и настраиваемые пути сохраняют возможность будущего переезда.
3. Локальный runtime запускает обычные процессы под учётной записью локального запуска без системной песочницы. Отдельная рабочая копия не объявляется защитной границей. Сохраняются отмена, таймауты, остановка дочерних процессов, события и сохранение Git-работы.
4. Подготовка окружения становится общей доменной операцией для реализации и независимой проверки. Рецепт задаёт версии инструментов и команду подготовки. Кешируются скачивания; установленные зависимости между несовместимыми рабочими копиями не переносятся.
5. Независимая проверка выполняется на закреплённом коммите в отдельной чистой копии. Проверяемые исходники не могут быть незаметно изменены подготовкой или проверкой. Самоотчёт агента не заменяет машинного результата.
6. Профиль исполнителя содержит выбранные CLI и модель для роли. Профили реализации и ревью задаются отдельно в проекте; доработка использует профиль реализации. Валидация совместимости происходит до исполнения. Автоматического fallback на другой CLI нет.
7. Первоначально активен Codex. Адаптер Claude Code и генерация его формата сохраняются, но существующие установка, авторизация и настройки Claude Code на VPS не изменяются, и фабрика его не запускает.
8. Общий инструментарий имеет один каталог, закреплённые источники и опубликованную версию. Генераторы доставляют настройки нужному CLI на Mac; структура допускает будущую доставку на другую машину без отдельного источника. У каждого имени навыка один источник; зависимости навыков и различия интерактивной/автоматической работы учитываются явно.
9. Каталог включает Pocock/pstack, Context7, Exa, локальный Graphify и Playwright. Для Playwright сохраняются воспроизводимые тесты и CLI с навыком; MCP доступен для нужных интерактивных сценариев. Секреты и история сессий не входят в каталог и не переносятся вместе с ним.
10. Бесплатный профиль Exa ограничен поиском и чтением страниц, Context7 использует бесплатный доступ, Graphify работает локально только с кодом без модельных backend, Playwright исполняется локально. Запрещены автоматическая оплата, платные API и скрытый запуск Claude Code. Удалённый сервис может менять ограничения независимо от закреплённой версии клиента.
11. Доступность инструмента проверяется в реальном окружении запуска. При исчерпании квоты допустимы другие достаточные источники; обязательные доказательства остаются обязательными. Недостаток данных останавливает зависимую задачу с причиной и не включает платный режим.
12. Граф кода относится к конкретной рабочей копии и актуализируется после её изменения. Он помогает навигации; итоговые выводы подтверждаются исходниками и тестами. Индекс не переносится между несовпадающими версиями как заведомо актуальный.
13. При старте сохраняется неизменяемый снимок согласованного плана: задачи и ожидаемые результаты, обязательные проверки, разрешённые особые изменения, границы релиза, профили исполнителей и версия инструментария. Изменения оставшейся работы создают явную новую редакцию с сохранением истории решения.
14. Постоянное состояние связывает задачу с попытками реализации, ревью, доработки и восстановления. В нём сохраняются бюджеты, переходы этапов, намерения внешних действий и доказательства выпусков. Физическая схема выбирается в рамках существующих репозиториев данных; миграции сохраняют прежние идентификаторы и историю.
15. Операции API подключения, настройки профилей, согласования и запуска плана, изменения его оставшейся части, отмены, восстановления и чтения результата вызывают единую доменную логику. CLI и UI используют ту же логику через существующие поверхности. Отдельный интерфейс только для тестов не вводится.
16. Повтор команды или рестарт не должен повторно создавать уже подтверждённый внешний эффект. Намерение сохраняется до внешнего действия; после прерывания фабрика сверяет PR, merge и deploy с площадкой. Неизвестный исход не трактуется как безопасный отказ.
17. Потеря модельной сессии не объявляется её продолжением. Фабрика сохраняет доступную Git-работу и создаёт связанную попытку в пределах прежнего бюджета. Восстановление покрывает реализацию, ревью и доработку; отменённая работа не перезапускается автоматически.
18. Начальные ограничения проекта: две попытки ремонта окружения, три доработки при подтверждённом прогрессе, 60 минут на запуск и три часа активной работы на задачу, включая подготовку и проверки. Ожидание внешней проверки учитывается отдельно, максимум час на этап. Настройки доступны владельцу; перезапуск не обнуляет расход.
19. Прогресс подтверждается устранением воспроизводимого дефекта или прохождением ранее падавшей обязательной проверки. Новая формулировка прежней ошибки не продлевает цикл. Ошибки реализации, окружения, внешнего сервиса и production имеют различимые причины и допустимые действия восстановления.
20. Ревью и проверки обязательны для задачи фабрики независимо от выбранного CLI. Merge относится к проверенному SHA на актуальной базе с сохранением обязательных проверок площадки. Смена имени роли не предоставляет обхода ревью.
21. Обычный код, зависимости, lockfile и сборка проходят автоматически после проверок. Изменения прав доступа, разрушительные миграции и правил фабрики требуют конкретного разрешения в плане либо отдельного решения. Общая формулировка цели не считается разрешением на произвольные особые изменения.
22. Проверка готовности проекта охватывает окружение, подготовку, quality gate, права, merge и доставку. Проект можно зарегистрировать и настраивать, но автономное исполнение до готовности запрещено. Существенное изменение настроек требует обновить доказательство готовности.
23. Подключение существующего репозитория сохраняет стек и работающую доставку; необходимые изменения предлагаются одним PR. Создание нового проекта использует предварительно согласованный стек. Первые рецепты покрывают Python/uv, JavaScript/TypeScript с менеджером проекта и Go; другие стеки допускаются с явным рецептом.
24. Seeds остаётся внутренним механизмом задач и планов. Mulch выключен для новых проектов по умолчанию, а существующая память сохраняется. Владельцу не требуется ручное обслуживание CLI этих инструментов для обычной работы.
25. Граница релиза задаётся планом. По умолчанию весь план имеет один deploy после завершения задач; промежуточная публикация требует явной границы. После merge задача может ожидать выпуска; план не считается успешным до проверки всех обязательных выпусков.
26. Проверенный выпуск подтверждается тремя согласованными проверками: идентичность опубликованной версии, доступность приложения и работа основного пользовательского сценария. Сведения площадки и работающего приложения должны согласовываться. Сценарий безопасен для рабочих данных.
27. Неудачный выпуск возвращает последнюю проверенную версию только при подтверждённой совместимости предыдущего приложения с текущими данными. После возврата выполняются те же проверки. Отсутствие предыдущей версии, неизвестная совместимость, необходимость обратного изменения данных или неподтверждённое восстановление приводят к остановке проекта с объяснением.
28. Исправление неудачного выпуска связано с исходной задачей, использует оставшийся бюджет и снова проходит полную цепочку. Следующие этапы проекта ждут; остальные проекты могут продолжать работу.
29. UI показывает одну доменную задачу и её цель, описание, текущий этап, проверенный результат, опубликованность и требуемое действие. Краткий результат опирается на сохранённые доказательства. Попытки, события и сырые промпты доступны как диагностика, а не как основное содержание карточки.
30. Основная навигация содержит только Задачи, Проекты и Настройки. Планы и выпуски размещены внутри проекта. Прежние технические разделы не сохраняются в скрытом списке More; старые ссылки ведут к подходящему результату или диагностике с сохранением истории.
31. Удаляются Pi, Docker-исполнение, автоматические патрули, внешние трекеры и четыре отдельных расширения: judge, campaign-controller, audit-log, tracker-conformance. Общая необходимая логика предварительно переносится к актуальному владельцу. Встроенное восстановление и диагностика сохраняются. Решение о Docker касается runtime фабрики и не запрещает существующую контейнерную доставку приложения проекта.
32. Удаление функций включает зависимости, установочные команды, активные настройки и устаревшие инструкции. Исторические данные остаются читаемыми. Публичные документы при удалении получают указатель на преемника или запись о завершении поддержки.
33. Новая версия сначала запускается на Mac с отдельным тестовым состоянием. Перед обновлением рабочей установки создаётся резервная копия; её восстановление проверяется отдельно без исполнения рабочей очереди. Защита локального API сохраняется; сервер не публикуется в сеть ради этого этапа.
34. Обновление рабочей локальной установки выполняется после приёмки: прекращаются новые старты, завершается активная работа, сверяются внешние действия, сохраняются база, история, очередь, рабочие копии, изменения и сведения о публикациях. Никакие данные на VPS сейчас не переносятся.
35. Рабочую очередь исполняет только одна версия фабрики. Возврат версии требует остановки нового процесса и сверки сделанных им действий; запуск устаревшей копии параллельно запрещён. Задел переезда ограничен настраиваемыми корнями данных и исполняемых файлов, явными платформенными различиями и сохранением идентичности данных; рабочий Linux-деплой не заявляется.
36. Обновление и откат самой фабрики учитывают активные задачи и совместимость схемы данных. Остановка службы не должна скрывать незавершённый внешний эффект; возврат старого исполняемого кода сам по себе не доказывает восстановление.

## Testing Decisions

1. Хороший тест проверяет наблюдаемое поведение: результат команды, состояние задачи, доказательство проверки, внешний эффект, сохранение истории и действие владельца. Он не закрепляет внутреннюю разбивку функций, порядок приватных вызовов или случайную форму реализации.
2. Основная граница проверки — существующий публичный HTTP API работающей фабрики. Сквозной сценарий подключает проект, проверяет готовность, запускает согласованный план и наблюдает проверенный выпуск и историю. Компоненты, которые невозможно достоверно проверить через API, получают ограниченные проверки на существующих внешних границах.
3. Пользовательский сценарий проверяется браузером поверх того же API: подключение проекта, выбор профилей, запуск, чтение результата, отмена и допустимое восстановление. Это проверяет понятность интерфейса и не дублирует всю серверную матрицу сбоев через клики.
4. Для воспроизводимых отказов используются существующие контракты runtime и Git-площадки с контролируемыми ответами. Сама координация и постоянное состояние остаются настоящими. Время управляется существующими точками подстановки там, где это возможно; тесты не должны ждать реальные часы для проверки лимитов.
5. Предшествующие образцы — сценарии acceptance с запуском сервера и HTTP-клиентом, интеграционные тесты цепочки реализация/ревью/доработка, проверки deployment gate с FakeForge и постоянными репозиториями, тесты независимой проверки, восстановления и бюджетов.
6. Предшествующие браузерные образцы — workspace, панель задачи, production delivery, fixture boot и общий openCase. Они дают основу для размеров экрана, тем, перехвата ответов и воспроизведений. Проверяются также пустые, загрузочные, ошибочные и неполные данные.
7. Реальные процессы проверяются на текущем Mac: подготовка чистой копии, запуск агента, отмена дерева процессов, таймаут, сохранение Git-работы и независимая проверка без системной песочницы. Настраиваемые пути проверяются в разных временных каталогах. Живая проверка Linux отложена и не является условием текущей приёмки.
8. Для профилей и инструментария проверяется фактически полученная конфигурация и доступность инструментов из запуска. Изменение профиля или версии пакета не меняет активный план; несовместимая пара CLI/модель отвергается заранее. Проверяется отсутствие изменений Claude Code на VPS и обращений к запрещённым backend.
9. Бюджеты проверяются на границах лимита, после рестарта, при недостающих измерениях, отмене, повторяющемся отказе и доказанном прогрессе. Нехватка бюджета блокирует зависимую работу, сохраняя работоспособность другого проекта.
10. Намеренные остановки процесса выполняются до и после внешнего эффекта PR, merge и deploy. После восстановления проверяются сверка площадки, отсутствие дубликатов, сохранение идентификаторов и корректная причина остановки при неизвестном исходе.
11. Снимок плана проверяется изменением исходного тикета, проекта и каталога после старта. Активная версия остаётся прежней; явное согласованное изменение применяется только к оставшейся работе и сохраняет историю.
12. Приёмка доставки включает план из нескольких задач с одним выпуском в конце и план с отмеченным промежуточным выпуском. Проверяются неверный SHA, незавершённый workflow, HTTP 200 при неработающем пользовательском сценарии, неизвестный исход dispatch и отсутствие доказательств готовности.
13. Rollback проверяется как восстановление приложения, а не успешный возврат команды. Отдельные случаи: совместимые данные, деструктивная миграция, неизвестная совместимость, отсутствие предыдущего проверенного выпуска, провал проверки после возврата и исчерпание бюджета исправления.
14. Бесплатные квоты и недоступность MCP моделируются через контролируемые ответы. Проверяется как продолжение с достаточными альтернативными источниками, так и остановка при недостающей обязательной информации; платного перехода и пропуска проверок нет. Затем выполняются ограниченные живые проверки бесплатного доступа с текущего Mac.
15. Проверка обновления и восстановления использует непустые историю и очередь, сохранённую Git-работу и незавершённые внешние действия. Сравниваются идентичность данных до/после, отсутствие дубликатов и невозможность двух владельцев очереди. Резервная копия действительно восстанавливается в отдельном локальном окружении; межмашинный перенос сейчас не выполняется.
16. Браузерная приёмка выполняется на ширинах 393px и 1440px в светлой и тёмной темах с проверкой доступности. Исправления UI-дефектов начинаются с падающего воспроизведения. Снимки с ноутбука не становятся новыми эталонами.
17. Общие проверки репозитория должны пройти на финальных входах каждого изменения; повторный полный прогон без изменения входов не требуется. Браузерная приёмка выполняется отдельно. Удаление теста допустимо вместе с удалённой функцией, но не вместо исправления регрессии.
18. Живая приёмка сначала проводится на отдельном тестовом проекте: обычный код, зависимость, UI, отказ подготовки, рестарт, квота и неудачный deploy с восстановлением. Только затем выполняется аудит пилотного проекта и малая согласованная задача. Искусственные аварии не проводятся на рабочем production.
19. Для приёмки сохраняются исходный и итоговый SHA, версия плана и инструментария, результаты подготовки, ревью, проверок, merge, deploy и rollback. Время, токены, попытки и ручные вмешательства учитываются без публикации приватных данных. Скрытый ручной ремонт исключает успешную автономную приёмку.

## Out of Scope

- Развёртывание фабрики на VPS, изменение его служб и авторизации, перенос туда очереди, настройка удалённого HTTPS-доступа и резервирования. Это будущий этап по отдельной команде владельца.
- Обещание непрерывной работы при выключенном или спящем Mac. Закрытие вкладки интерфейса и остановка устройства имеют разный эффект.
- Распределённая фабрика, несколько координаторов одной очереди и использование Mac как удалённого автоматического исполнителя VPS.
- Системная песочница, Docker-runtime фабрики, Pi, автоматические патрули, внешние трекеры и удаляемые отдельные расширения.
- Подключение, переавторизация, изменение конфигурации или использование Claude Code на VPS на текущем этапе.
- Новые провайдеры моделей помимо сохраняемых адаптеров и автоматический переход на другого исполнителя.
- Платные MCP, платные модельные backend Graphify, автоматическая покупка квот и обещание безлимитного бесплатного удалённого сервиса.
- Автоматическое включение несогласованных идей и произвольное изменение активного плана вслед за редактированием тикетов.
- Переписывание существующих проектов на другой стек ради фабрики и универсальная поддержка любого стека без явного рецепта.
- Произвольное создание платной инфраструктуры приложения. Фабрика подключает и проверяет согласованную схему deploy; новая площадка требует отдельного решения.
- Автоматическая разрушительная миграция данных без конкретного разрешения и rollback с непроверенной совместимостью данных.
- Бесконечные повторы, восстановление неизвестного внешнего исхода слепым повторным запросом и гарантия продолжения потерянной модельной сессии.
- Межмашинный перенос рабочей очереди в текущем этапе, искусственные аварии в production пилота и параллельный запуск старой копии очереди для восстановления.
- Удаление исторических записей запусков, существующей памяти проектов или несохранённой Git-работы под видом очистки.
- Публикация приватных адресов, credentials, конфигураций частных проектов и их сырых логов.
