# Приёмка подготовки, доставки и подключения

## Подготовка и ограниченный ремонт — 17–19, 24

Общий preparation runner используется исполнителем и независимой проверкой.
Рецепты и версии инструментов сохраняются в project settings; рабочие копии
не делят node_modules или .venv. Реальные fixture-проекты Bun, uv и Go прошли
подготовку, смену зависимости, отказ установки и отмену процесса.

Повторяется только временный сбой загрузки: транспорт, HTTP 429/5xx. Прежде
чем повторить команду, фабрика резервирует repair в бюджете исходной задачи.
Один этап допускает не больше двух повторов; бюджет задачи общий между
подготовкой, ревью и исправлением выпуска. Неверный lockfile, версия,
недоступный инструмент или отсутствие утверждённого бюджета дают остановку.
Рабочая копия и изменения задачи сохраняются. События repair_started,
repair_stopped и preparation.failed объясняют действие и причину.

Общий run deadline включает материализацию, подготовку, агента и проверку.
После каждого этапа следующий получает оставшееся время.

## Границы выпуска и восстановление — 28–31

Согласованный snapshot фиксирует настройки доставки и releaseAfter задач.
Промежуточный merge создаёт release_pending без deploy. Последняя открытая
задача или явная граница выпускает ровно один SHA. Перед внешним действием
сохраняется durable effect; неизвестный исход сверяется с площадкой и не
вызывает повторную публикацию. Ожидание ограничено.

Успех требует завершённого workflow, точного SHA на площадке и в приложении,
доступности и согласованного сценария. HTTP 200 без ожидаемого содержания
сценария не проходит. Настройки проверок фиксируются в плане. Для закрытых
приложений существует отдельный контракт доказательства из workflow:
`src/projects/release-workflow-proof.ts`.

При отказе допускается один rollback на последнюю полностью проверенную
версию, только при явно зафиксированной совместимости application-only и
основании. Неизвестная совместимость, необходимость обратной миграции или
отсутствие предыдущей версии останавливают проект. Rollback проходит те же
три проверки. Его отказ не повторяет возврат бесконечно. Проверенный возврат
создаёт решение repair; координатор проводит связанное исправление через
обычный бюджет, реализацию, ревью, merge и delivery.

## Готовность существующего и нового проекта — 32–33

GET readiness показывает доказательство и актуальность; POST readiness/check
проверяет Codex, профили, рецепт, независимый gate закреплённого SHA, права
push через dry-run, merge policy и delivery workflow. Код выполняется в
одноразовой копии. Настройки и исходный SHA входят в fingerprint; их изменение
делает прежнее доказательство неактуальным. HTTP запуск плана без готовности
запрещён, а утверждённый snapshot сохраняет проверенное доказательство.

Setup предлагает один PR на детерминированной ветке. Он сохраняет manifest,
зависимости и существующие application release scripts. При необходимости
checkout workflow привязывается к SHA, а автоматические триггеры заменяются
явным dispatch, чтобы соблюдались границы плана. Повтор ищет существующий PR.

Создание проекта сначала возвращает preview стека, репозитория и настроек.
Требуется подтверждение точного fingerprint; неподдержанный шаблон отвергается.
Текущий шаблон — Go/React/TypeScript/Bun. Повтор команды сверяет журнал создания
и существующий private repository. Новый проект остаётся неготовым до того же
readiness цикла; отсутствие доставки не даёт фиктивный успех. Mulch не включается
автоматически.
